# Innovation Scout Skill

## 目标

把“有什么值得做”变成“为什么值得做、怎么做第一版、如何验证”。优先输出能被 WeaveMind 现有工具链执行或沉淀的方案：Skill、工具、MCP、RAG 工作流、微信入口能力、团队协作流程、自动化评审流程。

## 工作流

1. **界定场景**
   - 明确目标用户、使用入口、当前痛点、成功标准。
   - 如果用户只说“找点创新”，默认围绕当前仓库能力做增量创新，不停下来追问。
   - 用一句话写出待验证假设：`如果为 {用户} 在 {场景} 提供 {能力}，那么 {指标/体验} 会改善，因为 {洞察}`。

2. **收集证据**
   - 内部证据：优先读 `README.md`、`CLAUDE.md`、相关模块和现有 Skill，识别已有能力边界。
   - 外部证据：使用联网搜索或 GitHub 搜索时，保留来源链接、日期和可借鉴模式。
   - 只把外部资料当启发，不把第三方实现直接照搬。

3. **生成机会**
   - 至少产出 3 个方向，覆盖不同创新杠杆：工作流、接口形态、记忆/RAG、协作、验证、分发。
   - 每个方向用“用户触发语 + Agent 行为 + 输出产物 + 验证方法”描述。

4. **收敛选择**
   - 用 `references/opportunity-scorecard.md` 给候选方向打分。
   - 优先选择高契合、高可验证、低集成风险的方向；新奇但难验证的方向只作为后续路线。

5. **落地蓝图**
   - 若方案是 Skill，按 `references/skill-blueprint.md` 输出或创建 `SKILL.md`。
   - 蓝图必须包含：触发条件、核心流程、工具/资源使用、反模式、验收用例、第一版边界。
   - 设计必须适配 WeaveMind 的渐进式披露：`description` 管触发，正文管流程，细节放 `references/`。

6. **验证**
   - 如果已修改仓库，至少运行与 Skill 解析相关的测试或做一次 `SkillRegistry` 加载检查。
   - 如果只是方案设计，给出 2-3 条可直接用来试跑的用户提示。

## 输出格式

优先使用这个顺序：

1. **调研发现**：列出可借鉴模式和来源。
2. **候选机会**：短表格，包含方向、触发语、价值、复杂度。
3. **推荐方案**：说明为什么选它。
4. **Skill 蓝图**：给出可落地结构。
5. **验证方式**：给出试跑提示或测试命令。

## 反模式

- 不要只给泛泛的 brainstorm 清单。
- 不要设计无法被当前工具链验证的“概念型”能力。
- 不要把联网搜索结果堆成摘要，必须转化为 weavemind 可执行流程。
- 不要把所有细节塞进 `SKILL.md`；超过正文核心流程的内容放到 `references/`。
