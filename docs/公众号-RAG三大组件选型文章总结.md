# 公众号文章总结：RAG 三大组件如何做工程选型

原文：<https://mp.weixin.qq.com/s/W6s6PtqwNMy340SoSSfQog>

标题：腾讯大模型二面：RAG 系统做完了，向量数据库怎么选、Embedding 怎么选、chunk 大小怎么定，选型理由你能说清楚吗？

作者/账号：吴师兄学算法

抓取时间：2026-07-01

## 核心观点

文章强调，RAG 系统的选型不能停留在“我用了 Milvus、某个 embedding 模型、512 token 分块”这种组件清单上，而要能回答：

- 为什么选这个，而不是其他方案。
- 用什么指标测过。
- 在业务数据上发现了什么问题。
- 组件之间是否联动调整。

文章给出的主线是：RAG 三大组件的选择，本质是在吞吐量、延迟、成本、领域适配四个维度上的权衡；每个选择都应该有实验数据和业务约束支撑。

## 向量数据库选型

文章比较了 Faiss、Chroma、Milvus、Weaviate：

| 方案 | 文章中的定位 | 主要优点 | 主要问题 |
| --- | --- | --- | --- |
| Faiss | 向量检索库 | 速度快，适合研究或小规模检索 | 不是完整数据库，缺少持久化、过滤、管理能力 |
| Chroma | 本地开发和 demo | 开箱即用，集成简单 | 并发和 P99 延迟不适合较严肃的生产环境 |
| Milvus | 生产向量数据库 | 持久化、属性过滤、分布式、监控能力 | 部署和运维复杂度高于 Chroma |
| Weaviate | 生产向量数据库 | 原生支持向量 + BM25 混合检索 | 如果团队已有 Elasticsearch/OpenSearch，内置 BM25 优势会弱化 |

文章中的案例最终选择 Milvus standalone，理由是：

- 规模约 5000 份文档、30 万条向量。
- 需要按保险产品线做属性过滤。
- 线上 P99 查询延迟要求小于 100ms。
- 团队已有 Milvus 运维经验。

文章提供的测试数据方向值得借鉴：不要只说“Milvus 更适合生产”，而要给出 QPS、P99 延迟、是否持久化、是否支持属性过滤等指标。

## Embedding 选型

文章认为，embedding 模型的核心问题不是榜单排名，而是领域偏差。通用模型在保险等垂直领域会把看似相近、但业务含义不同的概念混在一起。

文章比较了三类方案：

| 方案 | 文章中的结果 | 结论 |
| --- | --- | --- |
| text-embedding-ada-002 | 专业术语 Recall@5 较低 | 通用模型在领域术语上容易混淆 |
| BGE-large-zh | 召回有所提升 | 中文模型更适配中文，但仍缺领域知识 |
| BGE 领域微调 | 召回显著提升 | 高质量困难正负例比单纯堆数据更重要 |

关键经验：

- 领域数据中要构造“语义相近但业务含义不同”的困难负例。
- embedding 微调后必须重新向量化全部文档，旧向量和新 query 不在同一个向量空间。
- 微调后不仅要重建向量，还要重新评估向量库索引参数。

## Chunk 大小与切分策略

文章把 chunk 视为 RAG 系统中最容易被低估的环节。其观点是：固定 token 切分往往会破坏文档结构，尤其不适合合同、条款、制度、财务报表等结构化或半结构化资料。

文章列出的典型问题：

- 固定 512 token 会把一个完整章节切成半截语义。
- 表格按行切分后，下半段只剩数字，丢失表头。
- 列表项单独成块后，丢失前导句，无法判断它属于免责、条件还是操作步骤。
- 一个窗口里混入两个章节，会导致 embedding 表达混杂。

文章建议的 V3 方案：

- 按章节结构切分，而不是只按 token 数。
- 普通段落上限约 1024 token，关键条款可放宽到 1536 token。
- 表格整体保留；超长表格按“表头 + 数据行”切分。
- 列表前导句复制到每个列表项 chunk。
- overlap 不只是固定 token，而是按句子边界对齐。

## 三组件联动

文章最后强调，向量库、embedding、chunk 不是互相独立的：

- embedding 微调会改变向量空间分布，向量库索引参数可能要重调。
- chunk 越大，语义更完整，但可能超过 embedding 模型最佳输入长度。
- chunk 越大，向量数量越少，检索速度可能提升，但召回粒度变粗。
- 表格、列表、章节等结构处理，往往比单纯换 embedding 更影响召回质量。

## 对 WeaveMind 的启发

这篇文章对 WeaveMind 的通用资料 RAG 设计有三点直接启发：

1. 生产选型不能只沿用当前代码 RAG 的 Chroma。Chroma 适合作为本地开发和个人版存储，但企业版应预留 Milvus/Weaviate/OpenSearch 等生产级后端。
2. 资料 RAG 的 chunker 要独立于代码 RAG。PDF、Word、图片 OCR、表格、合同条款需要结构感知切分，不能复用代码文件的 AST/行切分思路。
3. 必须建立离线评测集。至少要记录 Recall@5、MRR、P99、QPS、引用准确率、无答案拒答率，否则无法说明选型是否真的变好。

## 面试式表达模板

可以把回答组织成四层：

1. 先说决策框架：吞吐量、延迟、成本、领域适配。
2. 再说向量库：本地验证 Chroma，生产服务 Milvus/Weaviate，混合检索用 OpenSearch/Elasticsearch 或 Weaviate 内置能力。
3. 再说 embedding：先用强基线模型，积累困难样本后做领域微调；微调后全量重建向量库。
4. 最后说 chunk：按文档结构切分，表格保留表头，列表保留前导句，overlap 按句子边界对齐。

## 需要保留的工程判断

RAG 没有绝对最优组件。真正的工程判断是：

- 当前用户规模是多少。
- 文档量和 chunk 量是多少。
- 允许的 P95/P99 延迟是多少。
- 是否需要多租户、权限过滤、审计、数据隔离。
- 是否能使用云模型，还是必须私有化部署。
- 业务语料是否强领域化，是否值得 embedding 微调。

这些约束比“排行榜第一”更重要。
