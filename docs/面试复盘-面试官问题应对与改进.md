## 1. Playwright 与 CDP 的取舍

**① 考察**：你为什么选 CDP（Chrome DevTools Protocol）而不是更流行的 Playwright？是不是真懂两者的本质差异。

**② 现状**：WeaveMind 通过 `chrome-devtools-mcp` Server 走 CDP，核心诉求是**复用用户已登录的本机 Chrome**（shared 模式）。

**③ 怎么回答**：

> 这是个取舍题，关键看需求。CDP 是底层协议，直接和浏览器内核通信；Playwright 是在 CDP 之上的高层封装，提供自动等待、跨浏览器（Firefox/WebKit）、更友好的 API。
>
> 我选 CDP 的核心原因是**登录态复用**：我的场景是连接用户**正在使用的、已经登录各种网站的那个 Chrome**，而不是起一个干净的自动化浏览器。CDP 可以通过远程调试端口 attach 到一个已运行的 Chrome 实例（读 DevToolsActivePort 拿 WebSocket 端点），天然继承用户的 cookie/session。Playwright 默认起独立的 browser context，虽然 `launchPersistentContext` 能指定 user-data-dir，但要求那个 profile 没被占用，没法 attach 到用户当前开着的浏览器，体验上要么抢占要么复制 profile。
>
> 另外 MCP 生态里官方的 chrome-devtools-mcp 就是 CDP 实现，用它能直接接入我的工具统一注册体系。
>
> 反过来，如果需求是**跨浏览器的稳定 E2E 测试**、不关心登录态，Playwright 的自动等待和选择器引擎会让脚本健壮得多——那种场景我会选 Playwright。所以不是谁更好，是 attach 已有浏览器 vs 全新可控环境的取舍。

**④ 改进**：可以在 isolated 模式下评估引入 Playwright 作为后端选项（独立环境用 Playwright 的自动等待更稳），shared 模式继续 CDP attach，做成可配置的浏览器后端抽象。

## 2. 用户级 Skill 含可执行脚本的安全 / 沙箱问题

**① 考察**：这是面试官点出的**真实安全隐患**。一旦 Skill 不只是 prompt 文本、而是包含可执行脚本（Claude 的 Skill 体系正是如此，SKILL.md 可带 scripts/），用户级/下载来的 Skill 就等于让 Agent 执行**不可信代码**。考你有没有安全意识和沙箱方案。

**② 现状（要诚实）**：

> 我现在的 Skill 是纯 Markdown 指令，body 只是注入 prompt，不执行脚本，所以**暂时没有这个攻击面**。但您点的这个问题很关键——如果要支持 Claude 那种带 scripts 的 Skill，安全就是必须先解决的前提。

**③ 怎么回答（讲清楚分层防御）**：

> 我会按"信任分级 + 沙箱隔离 + 权限收口"三层设计：
>
> **信任分级**：内置 Skill（随程序发布，可信）> 项目级（团队 git 仓库，较可信）> 用户级/下载（不可信，默认禁脚本）。不可信来源的 Skill 默认只允许注入 prompt，要执行脚本必须显式授权。
>
> **沙箱隔离**（按强度递增）：
> - 进程级：脚本不在主进程跑，用 subprocess + 资源限制（`resource.setrlimit` 限 CPU/内存、超时 kill）、最小化环境变量、只读工作目录；
> - 系统调用级：Linux 上 seccomp-bpf 白名单系统调用、namespace 隔离网络/文件系统；
> - 容器级：最彻底，每个不可信 Skill 在一次性 Docker 容器里跑，挂载只读卷、`--network none`、非 root 用户、cgroup 限流。生产环境我会选这个。
>
> **权限收口**：脚本要碰文件/网络/命令，统一走我现有的 PermissionPolicy + HITL 审批——危险操作弹给用户确认。等于把 Skill 脚本当成"另一种危险工具"纳入既有的审批闸口。
>
> **供应链安全**：下载的 Skill 校验签名/哈希、记录来源、首次运行强制人工审阅。

**④ 改进（写进 roadmap）**：
- Skill manifest 增加 `permissions`、`trust_level`、`scripts` 字段；
- 实现 `SkillSandbox`：默认 subprocess + rlimit + 超时，可选 Docker 后端；
- 脚本内的工具调用复用 PermissionPolicy/HITL；
- 下载 Skill 走校验 + 人工 review 流程。

> 加分点：你后端有 Redis 分布式锁、权限控制经验，可以说"沙箱的权限模型我在 RagNexus 用 RBAC + Bool Filter 下推做过类似的最小权限收口"。

## 3. Skill 下载实现

**① 考察**：Skill 生态化——从哪下、怎么装、怎么保证安全和版本。

**③ 怎么回答**：

> 我会做成类似包管理器的模型：
> - **来源**：远程 Skill Registry（git 仓库或对象存储），每个 Skill 是带 manifest 的目录（name/version/description/checksum/signature/permissions）；
> - **安装**：`skill install <name>` 拉取到用户级目录 `~/.weavemind/skills/`，校验 checksum 和签名，解析 manifest；
> - **安全**：下载默认 `trust_level=untrusted`，禁脚本，首次启用强制人工 review（见问题 2）；
> - **版本与覆盖**：复用我现有的三层覆盖机制（builtin < user < project），版本号支持锁定；
> - **隔离**：依赖（如脚本的 Python 包）装到 Skill 专属 venv，不污染主环境。

**④ 改进**：先把 manifest + checksum 校验 + 三层目录安装做出来（不含远程 registry 也能本地 `skill install ./path`），是低成本高展示度的增量。

## 4. 增量同步能否用 git 日志校验文件修改

**① 考察**：你现在 mtime + MD5，面试官提示 **git log 是更可靠的变更检测**。考你能不能评估方案优劣。

**② 现状**：`sync_before_search` 用 mtime 快筛 + MD5 精确确认两级检测（`rag/pipeline.py`）。

**③ 怎么回答（承认更优，但讲清适用边界）**：

> 您说的对，对**git 仓库内的文件**，git 是更准的变更源。mtime 有假阳性（touch、保存未改、checkout 切分支会重置 mtime），MD5 要读全文件内容算哈希。
>
> 用 git 的话：`git status --porcelain` 直接拿到工作区改动，`git diff --name-only <上次索引的commit>..HEAD` 拿到两次索引之间的变更文件，甚至 `git log` 拿到提交粒度的历史。优点是：① 准（git 用自己的 object hash，比我重算 MD5 更快也更可信）；② 能感知 rename/delete；③ 切分支、rebase 这些 mtime 会骗人的场景 git 不会错。
>
> 我现在没默认用 git 的原因是**通用性**：WeaveMind 要能索引非 git 目录（任意本地代码、下载的第三方库）。所以我的设计应该是**分层**：检测到 `.git` 就优先用 git diff 做变更检测，回退到 mtime+MD5 兜底非 git 场景。git 的 blob hash 还能直接当我的内容指纹，省掉重算 MD5。这样既准又通用。

**④ 改进**：
- 加 `GitChangeDetector`：仓库内用 `git diff --name-status <last_indexed_sha>..HEAD`，记录每次索引时的 commit SHA 到 metadata；
- 非 git 目录回退现有 mtime+MD5；
- 用 git blob hash 替代自算 MD5 作内容指纹。

> 这题答好能直接体现"通用性 vs 准确性"的工程权衡意识。

## 5. AST 新旧比较 / AST 能不能看到函数依赖关系

**① 考察**：两个递进的点。(a) 增量索引能否做到**函数级**而非文件级（AST diff）；(b) AST 能否提取**函数调用依赖**（往 Graph RAG / 调用图方向走）。这是 RAG 深度题。

**② 现状**：增量是**文件级** MD5，文件一变整个文件重新分块、重新 embed；AST 分块只提取结构（类/方法/函数/签名/docstring），**没有提取调用关系**。

**③ 怎么回答**：

> 分两层答。
>
> **(a) AST 新旧比较做函数级增量**：完全可行，也是我想优化的方向。现在文件改一行就整文件重 embed，浪费 embedding 调用。更细的做法是：对同一文件新旧两版各做 AST 分块，按"函数/方法签名 + 内容哈希"对比——只有 body 真正变了的函数才重新 embed，新增的加、删除的清理向量，签名没变 body 没变的跳过。这样把增量粒度从文件降到函数，索引成本大幅下降。代价是要维护 chunk 级的指纹和稳定 ID。
>
> **(b) AST 能不能看到函数依赖关系**：AST 本身能看到**一个函数体内部调用了哪些名字**（遍历 `ast.Call` 节点拿被调用的函数名），但要拿到**完整的"谁调用谁"调用图**，AST 不够，需要额外做**名称解析（resolution）**——因为 AST 里 `foo()` 只是个名字，要确定它指向哪个模块的哪个定义，得结合 import 解析、作用域分析。Python 是动态语言，还有动态调用、多态，静态分析只能做到近似。
>
> 实际工程做法：用 AST 提取 import 表 + 每个函数内的 call 名字，建一张"调用边"近似图（caller → callee），跨文件靠 import 路径匹配。这就从向量 RAG 升级到 **Graph RAG / 代码图谱**——检索到一个函数时，能把它的调用者、被调用者一起作为上下文带出来，对"这个函数在哪被调用""改它会影响谁"这类问题特别有用。更重的可以接 tree-sitter（多语言）或 LSP（精确解析）。

**④ 改进（分两期）**：
- 近期：chunk 级指纹 → AST diff 函数级增量索引；
- 中期：AST 提取 import + call 名字，建近似调用图，存进 metadata 或单独的图结构，检索时做"邻居扩展"（带出调用方/被调用方），形成轻量 Graph RAG。

> 这题能延伸到你简历的"混合检索/加权融合"，说"调用图可以作为融合排序的又一路信号"。

## 6. tool call 输入不存在的文件 / 产生幻觉 / 加入确定性

**① 考察**：LLM 会"幻觉"出不存在的文件路径去读，这是 Agent 可靠性的典型问题。考你怎么**用代码兜住 LLM 的不确定性**。

**② 现状**：有部分机制——工具连续失败 2 次本轮禁用、不可用工具直接返回可解释错误、`_maybe_force_search_code` 强制首跳检索。但**没有专门的"读不存在文件"前置校验**。

**③ 怎么回答（核心是"把不确定性约束在代码层"）**：

> 这正是我做 Agent 时最关注的点——**能用代码保证的确定性，不要交给 LLM 的概率**。针对幻觉文件路径，我会分几层：
>
> **前置校验 + 结构化纠错**：Read 工具执行前先判存在性，不存在不要只回"文件不存在"（LLM 容易再瞎猜一个），而是返回**带建议的结构化错误**：列出该目录下真实存在的相近文件名（编辑距离 / 同名不同后缀），引导 LLM 选真实路径。等于把"开放式幻觉"收敛成"在真实候选里选择"。
>
> **检索代替臆测**：我已经做了——对代码库问题强制先走 SearchCode（`_maybe_force_search_code`），让 LLM 基于真实检索结果里的真实路径去读，而不是凭记忆编路径。这本身就是"加确定性"。
>
> **失败熔断**：同一工具连续失败就本轮禁用并明确告诉 LLM 别再试、换方案——防止它拿着幻觉参数无限重试。
>
> **约束生成**：更强的做法是给 Read 的路径参数加约束/校验，或提供"列目录"工具让它先看真实文件树再读。
>
> 一句话：**Agent 的鲁棒性来自把环境的真实状态喂回给模型，并用代码闸门拦住明显错误的动作**，而不是指望 prompt 让它别幻觉。

**④ 改进**：
- Read/Edit 前置存在性校验，不存在时返回相近真实文件名建议；
- 路径优先用检索结果回填，减少裸路径输入；
- 把这套"校验→建议→熔断"抽成所有文件类工具共用的中间件。

## 7. 多 Agent：子 Agent 的上下文独立性

**① 考察**：多 Agent 的核心价值之一是**上下文隔离**——子 Agent 不该看到主 Agent 的全部历史（污染、浪费 token、串味），只接收任务、返回结果摘要。考你懂不懂这个。

**② 现状（要诚实）**：

> 我现在 Multi-Agent 的 Worker 是通过共享的 `MultiAgentState.messages` 拿全量历史的（`agent.invoke({"messages": state["messages"]})`），**上下文是共享而非隔离的**。这一点您提的对，是我可以改进的地方。我另外实现了一个 SubAgentTool（Task 工具）做了独立上下文，但还没接进主流程。

**③ 怎么回答（讲清为什么要隔离、怎么隔离）**：

> 子 Agent 上下文独立的价值有三个：① **防污染**——主 Agent 的探索性弯路、无关工具结果不该带进子 Agent，否则干扰判断；② **省 token**——子 Agent 只需要它那个子任务的最小上下文；③ **可并行**——上下文隔离了才能安全地并发跑多个子 Agent。
>
> 正确的设计应该是 **Supervisor 给子 Agent 下发的是"任务描述 + 必要输入"，而不是整个对话历史**；子 Agent 在自己独立的消息空间里完成 ReAct 循环，结束后只把**结果摘要**回传给 Supervisor，而不是把它的全部中间步骤倒回主上下文。这就是 Claude Code 的 sub-agent、以及 "context isolation" 的标准做法。
>
> 我会把现在的 Worker 改成：① Supervisor 构造精简的任务 prompt；② Worker 用独立 messages 跑（不继承主历史）；③ 只回传 last message / 结构化结果。我那个 SubAgentTool 已经是独立上下文的雏形，接进去即可。

**④ 改进**：
- Worker 节点不再传 `state["messages"]` 全量，改为 Supervisor 生成的任务指令 + 必要上下文片段；
- 子 Agent 用独立消息空间，仅回传结果摘要写进 `step_results`；
- 接入已实现的 SubAgentTool，统一"隔离上下文 + 摘要回传"模型。

## 8. 工作流 / 人工确认 / IO 中断 / 中断前保存状态 / 恢复可能路由到不同服务器 ⭐

**① 考察**：这是**最有分量、也最该让你发挥的题**。场景是：Agent 执行到一半需要人工确认（HITL）或等待 IO，会**中断**；而在分布式部署下，用户回来响应时请求**可能被负载均衡路由到另一台服务器**——所以中断前**必须把执行状态持久化到外部存储**，让任意一台服务器都能恢复。这是 Agent 工程从"单机玩具"到"生产服务"的分水岭，也正好踩中你 **Java 后端分布式状态管理**的强项。

**② 现状（诚实，但马上转到你会做）**：

> WeaveMind 现在是本地 CLI、单进程，HITL 是终端同步阻塞等待输入，没有这个分布式问题。但如果做成服务化，这就是必须解决的核心——而这恰好是我后端项目里做过的。

**③ 怎么回答（这是你的主场，要答得最深）**：

> 核心是**有状态的执行不能依赖进程内存，必须可持久化、可在任意节点恢复**——也就是 checkpoint + 无状态服务器。
>
> **状态外置（checkpoint）**：Agent 每个关键节点（每步 think/act 之后、尤其是中断点之前）把完整执行状态序列化到外部存储——LangGraph 原生支持 Checkpointer（Redis/Postgres backend）。状态包括：消息历史、当前节点、plan 进度、变量池、待审批的 tool call。中断（HITL/IO 等待）发生时，先 checkpoint 落盘，再释放这个请求。
>
> **无状态服务器 + thread_id 路由**：每个会话有唯一 `thread_id`。用户回来响应审批时，请求带 thread_id，**任意一台服务器**从 Redis/DB 按 thread_id 加载 checkpoint，从中断点继续——服务器本身不存状态，所以路由到哪台都行。这就解决了"可能路由到不同服务器"的问题。
>
> **人工确认的异步化**：单机是同步阻塞 input；服务化要改成**异步事件模型**——发起审批 → 持久化"待审批"状态 → 返回前端一个 pending 状态 → 用户审批是一个新请求 → 按 thread_id 恢复 → 注入审批结果继续。这跟我 FlowMind 工作流引擎里**节点中断、SSE 推状态、等外部回调再续跑**是同一套思路。
>
> **幂等与并发**：恢复要幂等（同一审批别重复执行已完成的步骤）——给每步一个 step_id，checkpoint 记录已完成 step，恢复时跳过；用户重复点审批用 Redis 分布式锁 + 状态机防重入。这些我在 RagNexus 用 Redis Bitmap 追踪分片上传状态、分布式锁防重复时实践过。
>
> **超时与补偿**：中断的会话设 TTL，长期不响应的标记过期；IO 类中断配合重试退避（FlowMind 里我做过固定/线性/指数退避 + 兜底输出 + 异常分支）。

> **这段一定要主动把三个项目串起来讲**：WeaveMind 提供 Agent 形态 → FlowMind 证明你会做工作流的中断/重试/状态流转 → RagNexus 证明你会做分布式状态（Redis）和异步链路（Kafka/SSE）。面试官会觉得你不是只会调 LangGraph，而是懂生产级有状态服务。

**④ 改进（WeaveMind 服务化 roadmap）**：
- 引入 LangGraph Checkpointer（先 SQLite 本地，再 Redis/Postgres）；
- HITL 从同步阻塞改为"持久化 pending 状态 + 异步恢复"；
- 会话用 thread_id 寻址，服务层无状态，支持水平扩展；
- step_id 幂等 + 分布式锁防重入；
- 中断会话 TTL + 过期清理。

## 9. 文件云存储方案

**① 考察**：Agent 处理/产出的文件（上传的代码、抓取的网页、截图、索引产物）在服务化后存哪。延续问题 8 的"无状态服务器"——文件也不能存本地磁盘。**这又是你 MinIO 的强项**。

**③ 怎么回答**：

> 跟状态外置同理，文件也不能依赖本地磁盘（多服务器、容器重启即丢）。我会用对象存储——自建用 MinIO，云上用 S3/OSS，接口兼容。
>
> **方案**：
> - **元数据与内容分离**：文件元信息（路径、大小、owner、版本、checksum）存 DB/Redis，文件体存对象存储，key 用 `tenant/session/hash` 组织；
> - **大文件异步链路**：分片上传 + Redis Bitmap 追踪分片状态，解析/索引这些重活丢 Kafka 异步处理——这套我在 RagNexus 做过 GB 级文件接入；
> - **去重**：内容哈希做 key，相同内容只存一份；
> - **访问控制**：预签名 URL（限时）给前端直传/直下，权限校验下推；多租户做逻辑隔离（我在 RagNexus 用 RBAC + 组织标签下推到检索层做过文档级隔离）；
> - **和 Agent 衔接**：Agent 的文件工具从直接读本地盘改为读对象存储抽象层，本地缓存热文件加速。

**④ 改进**：把 WeaveMind 的文件 IO 抽象成 storage backend 接口（本地 / MinIO / S3 可切换），截图、索引产物、抓取内容走对象存储。

> 这题几乎是送分——你简历 RagNexus 的 Kafka+Redis+MinIO 大文件异步处理就是标准答案，直接讲那套。

## 10. 让普通用户通过自然语言也能调用 Agent 能力

**① 考察**：产品视野——把开发者工具变成普通人能用的东西。开放题，考你的抽象和落地思路。

**③ 怎么回答（抽象 → 降门槛 → 安全）**：

> 核心是把"会写命令/懂工具"的门槛，降到"会说人话"。几个层面：
>
> **意图理解层**：用户说"帮我把这个网站的价格整理成表格"，Agent 自动拆解成"抓取→提取→格式化"的工具序列——这正是我 Plan-and-Execute 和工具自动选择在做的事，把自然语言映射到工具编排。
>
> **能力封装成"技能"**：把高频领域任务沉淀成 Skill（渐进式披露那套），普通用户不用懂底层工具，说出需求就触发对应 Skill 的完整方法论。等于给非技术用户预置了"专家知识"。
>
> **交互形态降门槛**：从 CLI 扩展到 Web/对话界面；关键步骤用人工确认（HITL）让用户"看得懂、敢点确认"；危险操作默认拦截，给普通用户安全护栏。
>
> **可解释与可控**：流式展示 Agent 在做什么（我已有 Hook 驱动的流式渲染），让用户全程可见、可中断，建立信任。
>
> **可靠性兜底**：普通用户更不能容忍幻觉和出错——所以问题 6 的确定性、问题 8 的状态恢复、问题 2 的安全沙箱，本质都是为了让"普通人也敢用"。
>
> 我的看法是：让普通用户用自然语言调 Agent，**技术上是工具编排 + 技能封装，体验上是可视化 + 可控 + 安全兜底**，两者缺一不可。

**④ 改进**：
- 沉淀面向终端用户的 Skill 库（非技术语言描述触发场景）；
- Web/对话前端 + 流式可视化 + 一键确认/中断；
- 默认安全模式（危险操作强制确认），降低普通用户翻车风险。

## 总结：这次面试暴露的能力地图

把面试官的问题归类，你会更清楚他在评估什么、你该补什么：

| 维度 | 对应问题 | 你的优势 / 缺口 |
|------|---------|----------------|
| **技术选型判断力** | 1 (Playwright/CDP)、4 (git/mtime) | 优势：能讲清取舍。补：主动讲"为什么不用更高级方案" |
| **安全意识** | 2 (沙箱)、3 (下载) | 缺口→机会：用后端 RBAC/最小权限经验补 |
| **RAG 深度** | 5 (AST diff/调用图) | 可延伸：从向量 RAG 谈到 Graph RAG |
| **可靠性工程** | 6 (确定性) | 优势：你已有熔断/强制检索，能讲透"代码兜住 LLM" |
| **多 Agent 理解** | 7 (上下文隔离) | 缺口：承认共享，讲清隔离方案 |
| **分布式/生产化** ⭐ | 8 (checkpoint)、9 (云存储) | **最大优势**：Java 后端三件套直接降维打击 |
| **产品视野** | 10 (自然语言) | 用已有能力（Plan/Skill/HITL/流式）串成产品叙事 |

### 三条核心应对策略

1. **诚实承认缺口，立刻给方案**。问题 2/7/8 现状是缺口，但"现在没做 + 我知道生产级该怎么做 + 这是我的 roadmap"比硬撑更显成熟。面试官问这些就是想看你有没有判断力，不是抓你没实现。

2. **把 WeaveMind 的不足，对接到你后端项目的成熟方案**。这是你最大的差异化——大部分 Agent 候选人只会调框架，你能从"单机 Agent 的局限"自然过渡到"FlowMind 的工作流中断/重试、RagNexus 的分布式状态/云存储/混合检索"。问题 8、9 几乎是为你量身定做的送分题。

3. **每个"为什么不用更强方案"都讲成取舍而非无知**。git vs mtime（通用性）、CDP vs Playwright（登录态）、文件级 vs 函数级增量（成本）、Plan 默认关（稳定性）——把每个简化决策讲成有意识的工程权衡。

### 落地优先级建议（投入产出比排序）

1. **问题 6（文件存在性校验 + 建议）** — 改动小、展示"确定性工程"意识，半天能做完；
2. **问题 7（子 Agent 上下文隔离）** — 接入已有 SubAgentTool，中等改动，直接补多 Agent 短板；
3. **问题 8（LangGraph Checkpointer）** — 先上 SQLite checkpointer 跑通中断恢复，是含金量最高的简历升级点；
4. **问题 4（git 变更检测）** — 加 GitChangeDetector，体现方案权衡；
5. **问题 2/3（Skill 沙箱 + manifest）** — 设计 + subprocess 沙箱雏形，补安全面。
